# AulaFlow 2.2 — Backup, restauración y seguridad operativa

Esta guía describe el procedimiento operativo del incremento 2.2 sobre el despliegue local con Podman.

## Principios

- El volumen `aulaflow-data` contiene la base activa.
- El volumen `aulaflow-backups` contiene las copias.
- Backup y datos activos tienen ciclos de vida independientes.
- La copia se crea con la Online Backup API de SQLite y se valida antes de declararse correcta.
- La restauración se realiza con AulaFlow detenido.
- Una copia inválida se rechaza antes de sustituir la base activa.
- Ningún backup, base real o secreto se versiona en Git.

## Requisitos previos

Debe existir la imagen local construida desde la rama actual:

```bash
bash container/build-image.sh
```

El despliegue normal conserva el volumen de datos creado en 2.1:

```text
aulaflow-data
```

Los scripts admiten variables para laboratorios separados:

```text
AULAFLOW_IMAGE
AULAFLOW_VOLUME_NAME
AULAFLOW_BACKUP_VOLUME_NAME
```

## Crear una copia

El backup puede crearse mientras AulaFlow está funcionando:

```bash
bash container/backup.sh
```

En la primera ejecución se crea, si es necesario, el volumen:

```text
aulaflow-backups
```

Una salida correcta tiene esta forma:

```text
Backup creado y validado: aulaflow-20260815T123456789Z.db
```

El nombre mostrado es suficiente para operaciones posteriores. No se expone la ruta física interna del volumen.

### Qué valida el proceso

Antes de devolver éxito se comprueba:

- fichero regular y no vacío;
- `PRAGMA integrity_check` = `ok`;
- `PRAGMA foreign_key_check` sin incidencias;
- historial `schema_migrations` presente;
- ausencia de versiones de esquema desconocidas.

Si la creación o validación falla, la copia incompleta se elimina.

## Listar copias

La CLI de mantenimiento puede listar nombres de backup cuando el volumen está montado. En operación normal basta conservar el nombre mostrado por `backup.sh`. La guía de recuperación manual usa el nombre exacto de la copia elegida.

## Restaurar

### 1. Detener AulaFlow

```bash
podman compose down
```

No elimines el volumen de datos.

### 2. Restaurar la copia elegida

```bash
bash container/restore.sh aulaflow-YYYYMMDDTHHmmssSSSZ.db
```

El script rechaza la operación si detecta un contenedor utilizando el volumen de datos.

El servicio de restauración vuelve a validar la copia, crea un fichero temporal junto a la base activa, valida ese temporal y solo entonces reemplaza la base.

### 3. Volver a arrancar

```bash
podman compose up -d
```

Después:

```bash
podman compose ps
curl -i http://127.0.0.1:8080/api/v1/health
```

El siguiente arranque vuelve a pasar por el migrador de AulaFlow, que también rechazará esquemas incompatibles.

## Copia dañada

Una copia corrupta debe producir un error semejante a:

```text
Operación no completada: La copia SQLite no ha superado la validación.
```

La base activa no debe cambiar.

No intentes “arreglar” una copia dañada sobrescribiendo manualmente el fichero activo.

## Retención

AulaFlow 1.0 no elimina backups automáticamente.

Política mínima recomendada para el entorno docente del profesor:

- conservar varias copias fechadas, no una única copia sobrescrita;
- mantener al menos una copia fuera del mismo equipo cuando se pase al mini-PC definitivo;
- no almacenar secretos junto a la copia;
- comprobar periódicamente que una copia puede restaurarse;
- eliminar copias antiguas de forma consciente según capacidad y necesidad docente.

La automatización de retención, cifrado o réplica queda fuera de AulaFlow 1.0.

## Seguridad HTTP

Todas las rutas que pasan por el pipeline estándar incluyen:

```text
Content-Security-Policy
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy
X-Content-Type-Options: nosniff
Cache-Control: no-store
X-Request-Id
```

Las dos últimas políticas pueden proceder de los escritores/manejadores ya existentes según el tipo de respuesta.

No se configura `Strict-Transport-Security` en el servidor HTTP local. HSTS solo tiene sentido cuando el acceso real se produzca por HTTPS y deberá establecerse en el terminador TLS/proxy.

## Cookies y sesiones

La cookie de sesión mantiene:

```text
HttpOnly
SameSite=Strict
```

y añade:

```text
Secure
```

cuando `AULAFLOW_SESSION_COOKIE_SECURE=true` en un despliegue HTTPS.

En HTTP local debe permanecer en `false`, ya que un navegador no devolvería normalmente una cookie `Secure` a un origen HTTP.

Las sesiones son efímeras y se pierden al reiniciar AulaFlow; la base restaurada no recupera sesiones antiguas.

## Logs

Los errores HTTP inesperados registran `requestId` y el tipo de excepción, pero no imprimen por defecto el stack trace completo. Los errores de arranque muestran una causa controlada y el tipo de excepción.

No deben registrarse:

- contraseñas;
- cookies de sesión;
- tokens CSRF;
- verificadores derivados;
- contenido completo de variables de entorno.

## Permisos

En la imagen:

- AulaFlow ejecuta como UID/GID 10001;
- `/opt/aulaflow` no es escribible por la aplicación;
- `/var/lib/aulaflow` es el área de datos;
- el volumen de backups se crea para UID/GID 10001.

## Ensayo de recuperación

El incremento no se cierra únicamente porque los tests sean verdes. Debe existir una prueba manual en Podman que:

1. cree datos reconocibles;
2. haga backup;
3. modifique los datos;
4. detenga el stack;
5. restaure la copia;
6. vuelva a arrancar;
7. confirme que se recupera el estado anterior;
8. pruebe una copia corrupta y confirme que los datos válidos no se pierden;
9. compruebe en navegador que las nuevas cabeceras no rompen la interfaz.

Para verificar tu instalación, realiza este recorrido y conserva tus comprobaciones locales. Las pruebas automatizadas están en `src/test/`.
