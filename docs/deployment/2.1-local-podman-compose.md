# Despliegue local de AulaFlow 1.0.0 con Podman y Compose

## Objetivo

Este documento describe el procedimiento reproducible validado en el
incremento 2.1 para construir y ejecutar AulaFlow mediante contenedores,
manteniendo SQLite fuera de la capa efímera y sin depender de Docker
Desktop ni de IntelliJ IDEA Ultimate.

El entorno local de referencia utilizado para la validación fue Bazzite
44 Kinoite con Podman 5.8.4 en modo rootless. El diseño del proyecto no se
acopla a Bazzite: `Containerfile` y `compose.yaml` utilizan formatos y
conceptos compatibles con otros entornos de contenedores cuando resulte
razonable.

## Qué se despliega

El flujo queda separado en cuatro piezas:

```text
código fuente
    ↓
Maven Wrapper + Java 26
    ↓
JAR ejecutable autocontenido
    ↓
imagen localhost/aulaflow:1.0.0
    ↓
contenedor + volumen SQLite
```

La imagen contiene el JRE de Java 26 y el JAR de AulaFlow. Maven, el JDK
de desarrollo y el código fuente no son necesarios para ejecutar el
contenedor una vez construida la imagen.

## Requisitos locales

Para construir la imagen:

- Java/JDK 26;
- Maven Wrapper incluido en el repositorio;
- Podman;
- acceso al registro necesario para descargar la imagen base de Eclipse
  Temurin.

Para utilizar `podman compose` hace falta además un proveedor Compose.
Podman delega esa función en un proveedor externo. En el entorno Bazzite
validado se utiliza `podman-compose`, instalado de forma aislada mediante
`pipx` para no sustituir el Podman suministrado por el sistema.

La disponibilidad puede comprobarse con:

```bash
podman --version
podman compose version
```

El mensaje que indica que Podman está ejecutando un proveedor Compose
externo es informativo.

## Construir la imagen

Desde la raíz del repositorio:

```bash
./container/build-image.sh
```

El script ejecuta primero:

```bash
./mvnw clean verify
```

y solo después construye la imagen mediante:

```bash
podman build \
  --format docker \
  -t localhost/aulaflow:1.0.0 \
  .
```

`--format docker` es deliberado. En las pruebas del incremento, Podman
ignoró la instrucción `HEALTHCHECK` al generar la configuración en el
formato OCI predeterminado. La incidencia y su recuperación están
registradas en `docs/incidents/INC-0004-healthcheck-ignorado-en-formato-oci.md`.

El motor continúa siendo Podman; el formato Docker se selecciona para
conservar los metadatos del healthcheck.

## Seguridad de la imagen

AulaFlow no se ejecuta como `root` dentro del contenedor. El proceso usa:

```text
uid=10001(aulaflow)
gid=10001(aulaflow)
```

La aplicación se instala en:

```text
/opt/aulaflow/aulaflow.jar
```

Ese directorio no es escribible por el usuario de AulaFlow.

Los datos variables se separan en:

```text
/var/lib/aulaflow
```

que sí es escribible por UID/GID 10001.

## Crear el volumen persistente

El volumen predeterminado se llama:

```text
aulaflow-data
```

Se crea mediante:

```bash
./container/create-volume.sh
```

El script es idempotente: si el volumen ya existe, no lo recrea. Cuando
lo crea, asigna UID/GID 10001 para que el proceso no privilegiado pueda
escribir SQLite.

Para una instalación o prueba separada puede utilizarse otro nombre:

```bash
export AULAFLOW_VOLUME_NAME=aulaflow-prueba
./container/create-volume.sh
```

`compose.yaml` montará el volumen elegido en:

```text
/var/lib/aulaflow
```

Por eso destruir el contenedor no elimina `aulaflow.db`.

## Primer aprovisionamiento

Una base vacía necesita nombre y contraseña del administrador inicial.
No existen credenciales predeterminadas en AulaFlow.

El nombre puede exportarse normalmente:

```bash
export AULAFLOW_ADMIN_USERNAME=admin
```

Para evitar que la contraseña quede escrita en el historial de la shell,
puede leerse de forma oculta:

```bash
read -s -p "Contraseña inicial de AulaFlow: " AULAFLOW_ADMIN_PASSWORD
echo
export AULAFLOW_ADMIN_PASSWORD
```

No debe utilizarse una contraseña personal en entornos de prueba ni
copiarse la credencial a documentación, capturas, commits o logs.

## Arrancar con Compose

Con la imagen construida y el volumen creado:

```bash
podman compose config
podman compose up -d
```

Comprobar el estado general:

```bash
podman compose ps
```

La aplicación queda publicada por defecto únicamente en el loopback del
host:

```text
http://127.0.0.1:8080
```

La publicación local predeterminada evita exponer AulaFlow a otras
máquinas de la red durante el desarrollo.

## Comprobar la salud

Desde el host:

```bash
curl -i http://127.0.0.1:8080/api/v1/health
```

La respuesta correcta incluye HTTP 200 y:

```json
{
  "status": "UP"
}
```

La imagen contiene además un healthcheck interno basado en el mismo
endpoint. `healthy` significa que AulaFlow responde correctamente; no se
limita a comprobar que exista un proceso Java.

Para las verificaciones habituales basta con `podman compose ps`. Las
comprobaciones mediante `podman inspect` se reservan para diagnóstico y
pruebas técnicas.

## Detener y recrear

Detener y eliminar los contenedores definidos por Compose:

```bash
podman compose down
```

El volumen se declara como externo y no se elimina con `down`.

Después del primer aprovisionamiento las variables iniciales pueden
retirarse:

```bash
unset AULAFLOW_ADMIN_USERNAME
unset AULAFLOW_ADMIN_PASSWORD
```

Un nuevo:

```bash
podman compose up -d
```

crea otro contenedor que reutiliza la misma base SQLite. El administrador,
tableros, columnas, tarjetas y demás datos persistentes deben conservarse.
Las sesiones permanecen en memoria y, por tanto, se pierden al recrear el
contenedor.

## Consultar logs

```bash
podman compose logs aulaflow
```

Para seguirlos mientras la aplicación está activa:

```bash
podman compose logs -f aulaflow
```

AulaFlow debe fallar de forma controlada ante una base vacía sin las dos
variables de aprovisionamiento. Los logs pueden explicar qué variable
falta, pero no deben registrar contraseñas, cookies ni verificadores.

## Configuración del Compose

`compose.yaml` admite estas variables del host:

| Variable | Valor predeterminado | Uso |
| :--- | :--- | :--- |
| `AULAFLOW_IMAGE` | `localhost/aulaflow:1.0.0` | Imagen que debe ejecutar Compose |
| `AULAFLOW_VOLUME_NAME` | `aulaflow-data` | Volumen SQLite externo |
| `AULAFLOW_BIND_ADDRESS` | `127.0.0.1` | Dirección del host donde se publica el puerto |
| `AULAFLOW_HOST_PORT` | `8080` | Puerto publicado en el host |
| `AULAFLOW_SESSION_COOKIE_SECURE` | `false` | Cookie `Secure`; debe ser `true` solo detrás de HTTPS |
| `AULAFLOW_ADMIN_USERNAME` | sin valor | Aprovisionamiento de una base vacía |
| `AULAFLOW_ADMIN_PASSWORD` | sin valor | Aprovisionamiento de una base vacía |

Dentro de la imagen se proporcionan estos valores adecuados al entorno de
contenedor:

```text
AULAFLOW_HTTP_HOST=0.0.0.0
AULAFLOW_HTTP_PORT=8080
AULAFLOW_DB_PATH=/var/lib/aulaflow/aulaflow.db
```

No alteran los valores predeterminados utilizados al ejecutar AulaFlow
directamente con Java fuera del contenedor.

## Secretos y archivos locales

No se debe versionar un archivo `.env` con credenciales. `.gitignore`
ignora `.env` y `.env.*` salvo el ejemplo permitido por el repositorio.

Tampoco deben versionarse:

- bases `.db`, `.sqlite` o `.sqlite3`;
- archivos `-journal`, `-wal` o `-shm`;
- logs;
- cookies o tokens de sesión;
- contraseñas reales.

## Despliegue limpio validado

El criterio de reproducibilidad se verificó clonando la rama en un
directorio temporal sin `target/`, ejecutando únicamente los scripts
versionados y creando un volumen nuevo.

El recorrido validado fue:

```text
checkout limpio
  ↓
./container/build-image.sh
  ↓
imagen con Java 26 y usuario 10001
  ↓
./container/create-volume.sh
  ↓
podman compose up -d
  ↓
aprovisionamiento
  ↓
creación de datos
  ↓
podman compose down
  ↓
retirada de credenciales iniciales
  ↓
podman compose up -d
  ↓
datos conservados y healthcheck correcto
```

La evidencia final se registra en:

```text
docs/release/1.0.0.md
```

La construcción de la imagen también se valida en GitHub Actions mediante
el job `Container image · Podman`, que comprueba el usuario no
privilegiado y la presencia de los metadatos de healthcheck.

## Compatibilidad y límites del incremento

Podman es el motor local de referencia, pero Docker Desktop no es un
requisito. La sintaxis del `Containerfile` y de Compose se mantiene
compatible cuando no contradice las decisiones de seguridad y
reproducibilidad del proyecto.

El incremento 2.1 no cubre todavía:

- despliegue definitivo en el mini-PC;
- proxy inverso ni HTTPS;
- backup y restore;
- Kubernetes;
- base de datos externa;
- publicación pública de imágenes.

Backup/restore y la revisión de seguridad se tratan en el incremento 2.2.
